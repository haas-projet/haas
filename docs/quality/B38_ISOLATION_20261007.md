# B38 — correction d'isolation du 7 octobre 2026

## Défauts et correction

L'ancienne branche `897c70d` déclarait B2 sous le runtime HAAS, retirait un middleware global par `withoutMiddleware`, conservait Sanctum stateful, utilisait la connexion par défaut (`DemoConnection::NAME = null`) et la clé d'application. Les probes conservés dans `MERGE_MADINA.md` et `probes/B38_ISOLATION.patch` avaient constaté le refus 403 de l'origine démonstration et deux cookies émis avec l'origine HAAS. Ce comportement interdisait la réception B38.

Le runtime `backend/demo` possède maintenant ses points d'entrée HTTP/CLI, configuration, environnement, migrations, routes, stockage et caches. `DemoApplication` fixe aussi les cinq chemins de cache et storage contre les overrides Laravel hérités. La configuration par défaut du framework et la découverte des packages sont désactivées ; aucun provider Sanctum, session, cookie, authentification, chiffrement HAAS, SMTP, notification ou queue n'est chargé. Le contrat B2 est séparé dans `docs/api/DEMO_OPENAPI.yaml` ; l'inventaire HAAS n'expose plus B2.

Seule la connexion PostgreSQL `demo` existe ; aucune configuration ou clé `APP_KEY` HAAS n'est utilisée. La clé HMAC d'idempotence est exclusivement `DEMO_IDEMPOTENCY_KEY`. La CI crée une vraie base fictive et son rôle NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION, révoque CONNECT public de la base métier, et génère/masque une clé B2 éphémère distincte.

Le runtime refuse les cookies, Authorization, hôtes et origines/Referer étrangers, y compris HAAS. CORS est exact et sans credentials, également sur les erreurs. Corps JSON borné à 2048 octets, trois champs stricts : référence `demo-[0-9]{4}`, entier de 1 à 1000000, devise fictive EUR. Aucun texte libre, URL ou identifiant personnel. Quota partagé PostgreSQL de 30 POST/minute/IP ; stockage maximum 5000 commandes.

Création, rejeu et conflit sont sérialisés par verrou transactionnel PostgreSQL. Garantie 24 h matérialisée et contrainte en SQL ; l'expiration est recontrôlée pendant chaque enregistrement, indépendamment du scheduler. La purge partage le verrou, supprime au plus 1000 commandes et conserve les intentions encore garanties. Réutiliser une clé expirée peut produire une nouvelle confirmation : limite explicite du protocole fictif, aucune promesse de persistance illimitée.

## Seconde revue : gardes de configuration et cache borné

La revue indépendante a trouvé quatre défauts dans la première correction : array encore accepté en production, anciennes clés de throttle/verrous non purgées et cache non borné, parent de cookies vide ou DNS avec casse contournant la comparaison, rôle/base DEMO mal configurés encore utilisables. Tous sont corrigés avant publication.

DemoRuntimeGuard valide et normalise les origines et le parent DNS (pas de credentials, chemin, query, fragment ou point DNS final). La configuration DEMO_ENV détermine le mode : array n’est accepté qu’en testing, même si APP_ENV hérité vaut testing. Hors testing le cache PostgreSQL partagé est obligatoire. La base HAAS est identifiée exclusivement par DEMO_HAAS_DATABASE. Aucun repli APP/DB : base/rôle démo nommés séparément, PostgreSQL seul, pas de connexion read/write/URL externe. Avant écritures HTTP/CLI, une requête réelle vérifie current_database/current_user, cinq flags privilégiés faux, absence de membership et CONNECT HAAS faux ; une base HAAS absente ou une preuve manquante ferme le service en 503.

GuardDemoCache est global, après ProtectDemoRequests et avant le routage/throttle. Il contrôle tous les POST, y compris le slash final normalisé par Laravel. CommandStarting protège aussi migrate:status et les commandes CLI qui accèdent à la base ou écrivent ; le processus réel demo:prune mal configuré quitte avec code1 et aucune écriture.

Les triggers PostgreSQL BEFORE INSERT prennent le verrou 238039 commun, purgent les expirations et limitent atomiquement cache à1000 lignes et cache_locks à100. Une clé existante est renouvelable à pleine capacité. P0001/B2_CACHE_CAPACITY est traduit par le renderer Laravel en 429 ; le Pipeline Laravel rend déjà les exceptions internes et ne permettait pas leur interception par un middleware extérieur. Pour DatabaseLock, la saturation retourne un verrou non acquis. Deux entrées successives du quota peuvent laisser un timer seul s’il reste un seul emplacement : cet état est borné et expire normalement. La purge retire les caches/verrous expirés en plus des commandes. Ordre de verrous 238038 puis238039 ; jamais l’ordre inverse.

Les fonctions PL/pgSQL sont explicitement VOLATILE et CREATE OR REPLACE pour supporter migrate:fresh répété. Seul READ COMMITTED est accepté ; les anciens snapshots sont refusés par la garde et le trigger. L’expiration utilise floor(epoch), aligné sur les secondes entières Laravel, pour ne pas purger prématurément une entrée pendant sa dernière demi-seconde. Un test SQL contrôle le calcul et la définition réellement installée.
