# Notifications internes — première livraison B29

GET /api/v1/notifications : liste privée paginée (20, maximum 50), compteur unread_count, tri date/UUID décroissant. PATCH /api/v1/notifications/{id} : booléen JSON read strict, session active et CSRF, sans aucun autre champ. Un administrateur n'accède pas à la boîte d'un tiers ; marquage tiers = 404. Les répétitions read=true conservent la première date, read=false efface cette date. Réponses no-store.

NotificationOutbox::record reçoit un UUID d'événement métier stable, un destinataire et un type autorisé **dans la même transaction PostgreSQL que le métier**. L'unicité destinataire/événement déduplique les retries. La transaction ne livre rien : le worker séparé ne voit que les intentions commitées. Un rollback ne laisse pas d'événement. L'échec d'enregistrement de l'intention annule le métier, plutôt que perdre définitivement une notification attendue.

`php artisan notifications:deliver` livre au maximum 100 intentions, avec FOR UPDATE SKIP LOCKED, insertion dédupliquée et marquage delivered_at dans la même transaction. Une panne de livraison ne touche pas le métier déjà commité, et conserve l'intention pour la prochaine exécution. Déclaration scheduler toutes les minutes ; surveillance de l'ancienneté des intentions requise en exploitation. Aucun worker de production n'a été activé. Pas de garantie de livraison immédiate. Le compteur lu est une photographie à sa requête, pas un flux temps réel.

Premier type fermé : profile.moderated. Message générique sans contenu, motif ni identité d'un signalant, chemin constant /me/profile (jamais l'ancienne URL publique). Aucun corps libre, code, adresse ou URL externe n'est stocké. La modération B31 fournit son premier producteur réel.

**B29 reste partiel** : les événements proposition/acceptation/réouverture/revue/rapport et les offres/cas/comparaisons n'existent pas encore dans ce socle. Chaque pilote ajoute un type par migration et un adaptateur autorisé : destinataire déterminé côté serveur, événement stable, visibilité courante appliquée avant liste/compteur/marquage et lien, aucune copie de titre retiré/secret. Un type non raccordé est refusé, pas livré fictivement. AC08 et AC84 globaux attendent les parcours réels. Les anciennes intentions livrées servent à la déduplication ; aucune purge de leur clé ne doit être introduite sans fixer la durée de garantie avec les producteurs.

## Raccordement B24 — Corrections demandées (Q12)

Le type fermé `capsule.review.changes_requested` raccorde maintenant la demande de corrections de B24. Le UUID du journal de revue sert d’événement stable ; le destinataire vient du propriétaire de la capsule relue sous verrou côté serveur. Intention, revue, transition, audit et idempotence sont dans la même transaction. Un rejeu ne crée aucun nouvel événement. La commande de livraison existante intervient après commit : sa panne conserve la décision et l’intention reprise ensuite.

La projection garde seulement six champs : `id`, `kind`, `message`, `target_path`, `read_at`, `created_at`. Message générique, chemin interne prévu par UX08 `/capsules/<UUID>/versions/<UUID>/edition` ; aucune note de revue, corps, adresse, titre ou donnée retirée n’est copié dans la notification. Avant pagination, compteur et marquage, il faut toujours être le propriétaire actuel actif et vérifié d’une capsule visible. Un retrait de visibilité, une perte de vérification ou un transfert exclut l’événement ; il ne détruit pas l’attribution historique et ne le transfère pas à une autre boîte.

Le downgrade des types refuse de supprimer des événements stables existants. Ses verrous transactionnels suivent la livraison : outbox puis boîte interne. Le downgrade du journal B24 refuse aussi toute revue portant un `reviewed_lock_version` connu, sous verrou avant DDL ; les anciennes notes sans snapshot restent anciennes sans révision reconstituée. Les remises à zéro de fixtures sur la base dédiée ne constituent pas un rollback de production.

Cette extension ne livre ni acceptation ni publication B25 et n’achève pas B29, AC08 ou AC84 dans tous les parcours. Aucun worker de production ni écran frontend n’est activé par ce raccordement.
